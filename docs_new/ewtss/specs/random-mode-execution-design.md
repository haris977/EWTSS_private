# Random-mode Execution — DRS-Engineer, WS2-only

**Status:** Active design record. Closes the *execution-flow* half of [B1.9](../design-backlog.md) for Random mode; the visual UI layout remains a [B1.1](../design-backlog.md) wireframe item.
**Audience:** drs-server developers (E/F — endpoints + `exercises` write), drs-bridge developer (A — `ResponseRouter` / `RandomGenerator`), drs_webapp developer (G — the surface), architecture lead.
**Decision basis:** [ADR-020](../decision-record.md#adr-020--scenario-is-the-definition-exercise-is-the-run-drs-server-owned-random-mode-is-ws2-only) — an *exercise* is a run owned by `drs-server`; Random mode is fully WS2-driven.

---

## 1. Goal

Define the complete runtime path for a **Random-mode exercise** driven entirely by the **DRS Engineer** from the **drs_webapp on WS2**, with **no dependency on the SG Operator, `Sg.App`, STK, or the SG workstation**. Random mode is for hardware checkout, development, and DRS-side diagnostics.

This spec covers everything that does **not** need wireframes: the drs-server REST surface, the `exercises` run record, the Kafka control message, and the lifecycle. The visual layout of the config + run-control views is [B1.1](../design-backlog.md).

## 2. Context

Random mode "replaces the scenario publisher with a per-variant random data generator inside the C++ parser. No `computed_links`, no STK, no scenario" ([architecture-overview §4.8](../architecture-overview.md)). Its control-plane producer was *already* `drs-server` (`drs.session.control`), so the only thing that ever tied it to WS1 was the location of the parameter-range config UI. ADR-020 moves that surface to the drs_webapp, making the mode WS2-only.

Contrast with Scenario mode (unchanged, SG-driven): `Sg.App` computes `computed_links` and publishes ticks; the run is a Scenario-mode `exercise`. See [command-flows §2.6 + §3.2](../command-flows.md).

## 3. Scope

**In scope:**
- drs-server REST endpoints for Random-mode configuration + run control.
- The `exercises` run record write (drs-server; `mode='random'`, `scenario_id` null).
- The `drs.session.control` start/stop/config message contract addition.
- Standalone vs Integrated behaviour for Random.
- Run lifecycle, idempotency, and failure handling.

**Out of scope:**
- Visual UI layout of the config + run-control views → [B1.1](../design-backlog.md) wireframes.
- Scenario mode (SG-driven) — see [scenario-management-design](scenario-management-design.md) + command-flows.
- Data-plane payload shapes (`hw.<variant>.<kind>`) → deferred to first-IRS work ([kafka-infra-layer-design §3.3](kafka-infra-layer-design.md)).
- Persisted, reusable "random profiles" — see §8 open questions (YAGNI unless the customer asks).

## 4. Design

### 4.1 Actors and flow

```
DRS Engineer        drs_webapp        drs-server            Kafka              drs-bridge
(WS2 browser)       (WS2)             (WS2)                 (WS2)              (WS2)
    │  configure ranges  │                 │                     │                  │
    │───────────────────►│                 │                     │                  │
    │  Start run         │                 │                     │                  │
    │───────────────────►│ POST /exercises │                     │                  │
    │                    │────────────────►│                     │                  │
    │                    │                 │─ write exercises row (mode=random,      │
    │                    │                 │   scenario_id NULL, scope, status)      │
    │                    │                 │─ publish drs.session.control          │
    │                    │                 │  {action:start, ranges} ───────────────►│
    │                    │◄── 201 {exercise_id, status:executing}                    │
    │                    │                 │                     │  ResponseRouter →  │
    │                    │                 │                     │  RandomGenerator(ranges)
    │                    │                 │                     │◄─ hw.<variant>.<kind> (generated bytes)
    │   live health/status view (WS)       │◄────────────────────│  (+ TCP-out to entity apps if Integrated)
    │◄───────────────────┤◄── WS broadcast ┤                     │                  │
    │  Stop run          │ POST /exercises/{id}/stop             │                  │
    │───────────────────►│────────────────►│─ publish drs.session.control{action:stop}─►│ RandomGenerator off
    │                    │                 │─ exercises.status=complete, ended_at        │
```

**No WS1 anywhere in this flow.** `Sg.App`, STK, and `computed_links` are not involved.

### 4.2 drs-server REST surface (add to `drs-server-openapi.yaml` as it lands)

| Method + path | Purpose | Body / returns |
|---|---|---|
| `GET /variants/{variant}/random-config` | Allowed parameter ranges + bounds for a variant (sourced from the drs-bridge YAML profile's declared min/max). | → `{ params: [{ key, min, max, unit }] }` |
| `POST /exercises` | Start a run. drs-server writes the `exercises` row and publishes the control message. | `{ mode:"random", scope:"standalone"\|"integrated", variants:[{ variant, ranges:{...} }] }` → `201 { exercise_id, status:"executing" }` |
| `POST /exercises/{id}/stop` | Stop the run. | → `{ exercise_id, status:"complete" }` |
| `GET /exercises/{id}` | Run status. | → `{ exercise_id, mode, scope, status, started_at, ended_at }` |

The `POST /exercises` shape is mode-general on purpose: a Scenario-mode run start (requested by `Sg.App`) is the same resource with `mode:"scenario"` + `scenario_id`. This keeps one run-lifecycle surface for both modes, consistent with `drs-server` owning the `exercises` table (ADR-020).

### 4.3 The `exercises` write

`drs-server` writes the run record (schema in [developer-handbook §10.2](../developer-handbook.md#102-execution--time-series-telemetry-schema-drs-server-writes)): `mode='random'`, `scenario_id = NULL`, `scope`, `status='executing'`, `started_at=now()`. `POST /exercises/{id}/stop` sets `status='complete'`, `ended_at`. The row is the parent of the telemetry `drs_sessions` produced during the run.

### 4.4 The `drs.session.control` message

`drs-server` publishes `start`/`stop` to `drs.session.control` — the single server→bridge run-control topic shared with Scenario mode (`Sg.App` is the producer there), **distinct from** the reverse-direction `drs.control` (drs-bridge → drs-server). `drs-bridge`'s `ResponseRouter` switches the addressed variant's session to `RandomGenerator(ranges)` on `start` and off on `stop` ([developer-handbook §12.4](../developer-handbook.md#124-the-responserouter)). The payload is pinned in [`contracts/kafka/drs.session.control.schema.json`](../../../contracts/kafka/drs.session.control.schema.json): a Random `start` carries `{action:"start", exercise_id, mode:"random", scope, variants:[{variant, ranges}]}`; `stop` carries `{action:"stop", exercise_id}`. The topic still needs provisioning in [`infrastructure/kafka/create-topics.py`](../../../infrastructure/kafka/create-topics.py) at implementation.

### 4.5 Standalone vs Integrated

Identical generation path; **Integrated** additionally TCP-outs the formatted IRS bytes to the connected entity-controller apps (drs-bridge already does this in Integrated mode) and benefits from the entity-reachability readiness check. The DRS Engineer selects scope at run start; no SG involvement in either.

### 4.6 Lifecycle, idempotency, failure

- **Idempotent stop:** stopping an already-complete run is a no-op returning current status.
- **Webapp disconnect mid-run:** the run continues — `drs-server` owns it, not the browser. On reconnect the webapp reads `GET /exercises/{id}` and resumes the live view.
- **drs-bridge restart mid-run:** on reconnect the bridge has no active random session; `drs-server` re-publishes the active control message (the `exercises` row is the source of truth for "what should be running"). *(Confirm against the roster/presence reconcile pattern — [drs-roster-reconcile-plan](../plans/drs-roster-reconcile-plan.md).)*
- **Concurrency:** multiple variants can generate under one Random exercise; one active Random exercise per deployment is the expected case (mirrors the single-active-exercise assumption in Scenario mode).

### 4.7 Time source (WS2-local)

Because Random runs must survive WS1 being powered off, they cannot depend on WS1 as the LAN Stratum-1 time server — and drs-server's time-sync engine auto-pauses a running exercise on `sync_lost`. Therefore **WS2 carries its own local NTP time reference** (a local-clock fallback so WS2 keeps serving coherent time when SG is absent), and for a Random exercise the sync gating is evaluated against WS2's local reference (not WS1). Scenario mode is unaffected (it needs WS1 anyway). Full discipline is specified in [time-sync-design §4.5 + §7.1](time-sync-design.md#45-ws2-local-time-source--for-ws2-only-random-mode); deployment reflected in [deployment-guide §1/§7](../deployment-guide.md).

### 4.8 Reporting — Random runs are non-reportable

A Random run has no scenario and no compute snapshot, and `reports` require both (`scenario_id` + `snapshot_id` NOT NULL — [scenario-management-design §4.6](scenario-management-design.md#46-report-durability-sketch)). **Random-mode exercises are therefore non-reportable by design** — they are hardware-checkout / diagnostic runs. drs-server rejects a report request for a `mode='random'` exercise. Post-run evidence for a Random run is the captured telemetry (`measurements`), reviewable live in the drs_webapp; a formal PDF report is a Scenario-mode capability only.

## 5. Testing

| Layer | What | Where |
|---|---|---|
| Unit (drs-server) | `POST /exercises` writes the row + emits the control message; stop closes it; range validation against variant bounds | `drs-server/tests/` (new) |
| Unit (drs-bridge) | `RandomGenerator` honours ranges; `ResponseRouter` mode switch on control message | `drs-bridge/tests/` (RandomGenerator already planned — [execution-plan §4.3](../v2-execution-plan.md)) |
| Integration (WS2-only) | Start Random run via drs-server → bytes on `hw.<variant>.<kind>` → webapp display, **with `Sg.App` not running** (proves WS1 independence) | drs-server + drs-bridge integration (graceful-skip if broker absent) |

The WS1-absent integration test is the executable proof of the ADR-020 decision.
